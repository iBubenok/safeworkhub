# Архитектура системы SafeWorkHub

## Обзор

SafeWorkHub — корпоративная SaaS-платформа по охране труда с платной подпиской. Система предоставляет единую точку доступа к базе знаний, экспертным консультациям, обучению и интерактивным сервисам для специалистов по охране труда.

## Архитектурный стиль

### Выбранный подход: Модульный монолит

**Обоснование выбора:**

При анализе возможных архитектурных подходов рассматривались следующие альтернативы:

| Подход | Преимущества | Недостатки |
|--------|-------------|------------|
| **Микросервисы** | Независимое масштабирование, изоляция сбоев | Сложность инфраструктуры, латентность, операционные затраты |
| **Классический монолит** | Простота разработки и развёртывания | Сложность масштабирования, связанность кода |
| **Модульный монолит** | Простота инфраструктуры + модульность кода | Требует дисциплины для поддержания границ модулей |

**Выбор модульного монолита обусловлен:**
1. **Этап MVP** — минимальная инфраструктурная сложность при сохранении возможности эволюции
2. **Команда** — один репозиторий проще для координации небольшой команды
3. **Производительность** — отсутствие сетевой латентности между модулями
4. **Путь миграции** — чёткие границы модулей позволяют выделить микросервисы при необходимости

### Доменные модули

1. **Auth Module** — аутентификация, авторизация, управление пользователями и организациями
2. **Subscription Module** — тарифы, биллинг, управление подписками
3. **Knowledge Base Module** — база знаний, НПА, шаблоны документов
4. **Consulting Module** — экспертные консультации
5. **LMS Module** — обучение, курсы, тестирование, сертификация
6. **Services Module** — интерактивные сервисы, калькуляторы, мастера

## Хранение данных

### Стратегия кэширования

| Уровень | Технология | TTL | Данные |
|---------|-----------|-----|--------|
| L1 | In-memory (приложение) | 60 сек | Конфигурация, справочники |
| L2 | Redis | 5-60 мин | Сессии, результаты поиска, часто запрашиваемые данные |
| L3 | CDN (Nginx) | 24 часа | Статические файлы, документы |

### Инвалидация кэша

Применяется паттерн Cache-Aside с событийной инвалидацией:
- При изменении данных публикуется событие
- Подписчики инвалидируют соответствующие ключи кэша
- Для критичных данных используется write-through

### Стратегия масштабирования по компонентам

| Компонент | Стратегия | Примечание |
|-----------|-----------|------------|
| API-серверы | Horizontal (stateless) | За load balancer, автоскейлинг по CPU/RPS |

| Celery Workers | Horizontal | Отдельные очереди по приоритету задач |
| Frontend | CDN + множество инстансов | Статика на CDN |

## Безопасность

### Принципы

1. **Defense in Depth** — многоуровневая защита
2. **Principle of Least Privilege** — минимальные необходимые права
3. **Zero Trust** — проверка на каждом уровне

### Меры защиты

| Угроза | Защита |
|--------|--------|
| SQL Injection | ORM, параметризованные запросы |
| XSS | CSP, экранирование, React по умолчанию |
| CSRF | SameSite cookies, CSRF tokens |
| Brute Force | Rate limiting, account lockout |
| Data Breach | Шифрование at-rest и in-transit |
| Session Hijacking | Secure cookies, короткий TTL токенов |

### Персональные данные

- Шифрование PII в базе данных (AES-256)
- Аудит-лог всех операций с ПД
- Поддержка права на забвение (GDPR-ready)
- Анонимизация данных для аналитики

## Отказоустойчивость

### Точки отказа и митигация

| Компонент | Риск | Митигация |
|-----------|------|-----------|
| API-сервер | Сбой инстанса | Несколько инстансов, health checks |
| PostgreSQL | Потеря данных | Streaming replication, WAL archiving |
| Redis | Потеря сессий | Redis Sentinel / Cluster, persistence |
| Внешние API | Недоступность | Circuit breaker, fallback, retry |

### Резервное копирование

- **PostgreSQL**: Ежедневные полные бэкапы + WAL shipping для PITR
- **Файлы**: Репликация между регионами S3
- **Конфигурации**: Версионирование в Git

### RTO/RPO цели

| Метрика | Значение | Комментарий |
|---------|----------|-------------|
| RPO (Recovery Point Objective) | 1 час | Максимальная потеря данных |
| RTO (Recovery Time Objective) | 4 часа | Время восстановления сервиса |

## Мониторинг и observability

### Три столпа observability

1. **Метрики** (Prometheus)
   - Системные: CPU, RAM, диск, сеть
   - Приложения: RPS, латентность, ошибки
   - Бизнес: активные пользователи, конверсии

2. **Логи** (Loki / ELK)
   - Структурированные JSON-логи
   - Корреляция по request_id
   - Retention: 30 дней (production)

3. **Трассировка** (OpenTelemetry)
   - Распределённые traces
   - Span-ы для ключевых операций
   - Интеграция с Jaeger/Tempo

### Алертинг

Критерии эскалации:
- **P1 (Critical)**: Сервис недоступен → немедленное оповещение
- **P2 (High)**: Деградация производительности > 50% → 15 мин
- **P3 (Medium)**: Ошибки > 1% → 1 час
- **P4 (Low)**: Предупреждения → ежедневный дайджест

## Границы MVP

### Входит в MVP

- Базовая аутентификация и авторизация (email/password)
- Управление организациями и пользователями
- База знаний с полнотекстовым поиском
- Просмотр НПА и шаблонов документов
- Базовый LMS (курсы, тесты)
- Простой биллинг (один тариф)
- Docker-окружение для development

### Не входит в MVP

- SSO/SAML интеграция
- Мобильное приложение
- Экспертные консультации с чатом
- Сложные интерактивные сервисы
- Kubernetes deployment
- Мультиязычность

## Допущения и решения

Все принятые архитектурные решения с обоснованием:

1. **Модульный монолит вместо микросервисов** — оптимально для MVP и небольшой команды
2. **PostgreSQL FTS вместо Elasticsearch** — достаточно для начальных объёмов, меньше компонентов
3. **Celery вместо альтернатив (Dramatiq, Huey)** — зрелость, мониторинг, документация
4. **React вместо Vue/Svelte** — размер экосистемы, доступность специалистов
5. **Tailwind вместо CSS-in-JS** — производительность, предсказуемость
